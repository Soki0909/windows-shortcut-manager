# #32 既存lnkの代表起動条件の検証

2026-11-17にローカルの対象テスト51件が成功。UNC共有とURI登録の2件はGitHubのWindows runner専用のためスキップした。ローカルではSDK 10.0.404を使用した。PRのCIでリポジトリの指定SDKによる結果を確認する。

## 発見

- 現行importerは既に全lnkを元パス参照にしていた。通常/最小化の読戻しはあるが、元リンクを直接Shell起動した場合との同等性は未確認だった。
- STARTUPINFOの保存値1/7を起動先で確認する試験を追加し、従来のExplorer参照経由が10になることを再現。原本の保存属性と起動先の受信値は別物として扱う。直接Shell起動との比較でも差分を確認したため、期待値を弱めず呼出し経路を修正する。
- `SetPath` は元リンクをexeへ平坦化した。`SetIDList` で元ファイルのPIDLを設定しても、`IPersistFile.Save` ではディスク保存時に参照が失われた。`IPersistStream` 保存では元PIDLと `AllowLinkToLink` を保持した。

## 検証範囲

隔離した一時フォルダと製品非同梱のLaunchProbeだけを使う。元HotKeyはリンク属性として保存・読戻しするが、キーを登録/押下しない。原本bytes・mtime・引数・作業フォルダ・表示属性・AppUserModelIDを確認する。個人の設定や管理リンク、インストール済み製品、Storeアプリは操作しない。

実画面の最小化や、実Storeアプリ固有の有効化/認証を検証したとは主張しない。

## 反映・監査の回帰

- 通常表示、最小化、AppUserModelID付きの3件で、元リンク直接起動、候補のテスト実行、反映で生成した管理リンクの実行結果を比較した。日本語引数、作業フォルダ、STARTUPINFOの表示方法が一致した。バックアップの作成、読取り監査の差分なし、原本bytes・mtime・HotKey・AppUserModelIDの保持も確認した。

- 参照フラグが欠けると、Windowsの読取り拒否または反映・監査の不一致になる。ローカルでは、フラグを取り除いたリンクをWindowsが読取り拒否した。正常に読めるデータでも、比較に必要な参照フラグがなければ不一致と判定する。
- 循環、管理フォルダ内への参照、相対参照、過剰な連鎖を拒否する。既存の通常リンクの読戻し、外部HotKey競合、バックアップ・反映・復元経路も対象テストで確認した。
