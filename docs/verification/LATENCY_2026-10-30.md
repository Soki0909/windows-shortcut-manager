# #115: real shortcut-key latency measurement

Owner machine, 2026-10-30. Manager was not resident. An owned Desktop .lnk used the otherwise free Ctrl+Alt+U; the installed 22 assignments and existing links were untouched. The owner physically pressed the test key ten times before and ten after an approved mitigation. Direct Shell execution was measured ten times in each phase. Owned copies/keys were removed after both sessions.

|Path / phase|n|Median to target code (ms)|Max (ms)|Median to Shown event (ms)|
|---|---:|---:|---:|---:|
|Direct .lnk / before|10|154.81|366.35|245.51|
|Physical HotKey / before|10|3086.43|3156.48|3174.32|
|Direct .lnk / after|10|190.63|366.16|285.45|
|Physical HotKey / after|10|139.92|194.28|237.74|

All target executions create a new process; binary/file caches are warm after direct trials. The raw field `requestToStartMs` means entry into the measured target method, **not** an OS process-creation event. Shown is a window lifecycle event, not a display-frame timestamp. The selected three keys are sampled by a test-only timer (no global hook), so input timestamp resolution is approximately a UI timer tick (around 5–20 ms under normal load). These limitations are much smaller than the roughly 3-second difference. With only ten samples use maximum rather than claiming a stable p95.

Before mitigation, read-only probes examined 794 windows and found eight non-responses belonging to two application processes. Both were also reported as not responding by Windows. The owner explicitly authorized normal close followed by forced termination if necessary for **only those two applications**. Afterwards 784 windows responded and the candidate list was empty. No driver, audio service, registry tuning or security setting was changed. Because both candidates were removed together, neither application alone is proven to be the culprit. The candidates may recur; the product provides an on-demand diagnostic and manual recovery guidance rather than silently closing other applications.

The measurement isolates the common Shell/launch stage using a disposable executable. It does not benchmark every installed app's cold start, perform automatic tests in personal Chrome, or promise every future shortcut will open in 140 ms. The owner reported normal apps/Web as well as Chrome affected; the common pre-target delay and direct/physical comparison explain the measured incident. Real Chrome regression separately covers Dispatcher/Worker and warm/cold operation in a dedicated profile. Website/Application/BAT resolution remains unchanged.

Primary references: Microsoft's [Shell HotKey delay explanation](https://devblogs.microsoft.com/oldnewthing/20120502-00/?p=7723), [WM_GETHOTKEY](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-gethotkey), and [SendMessageTimeoutW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagetimeoutw). The observed result is consistent with the documented response-wait mechanism; it is not a blanket assertion about every current Windows build or every unresponsive window.

Private evidence: `latency-20261030-153959`, `latency-after-20261030-154531`, `shell-latency-probe-before.json`, `shell-latency-probe-after.json`, and the owner's explicit confirmations in the task.
